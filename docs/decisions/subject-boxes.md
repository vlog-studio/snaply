## 1. 배경 — 꾸밈이 네 모서리에만 붙는다

글자 효과 · 이모지 스티커는 피사체 가장자리에 반쯤 걸치게 놓도록 설계됐다(`pipeline/sticker.py` `spots`,
`pipeline/text_accent.py` — 피사체 상자를 받으면 걸치는 자리 · 옆자리를 먼저 시도한다). 그런데 피사체 상자를 주는 곳이
없어 대부분의 무비에서 후보가 **안전 영역(`layout.SAFE`)의 네 모서리뿐**이다.

| 경로 | 피사체 상자 |
|---|---|
| 사용자가 컷을 고른 무비(`pipeline/accent_stage.py` `build_cuts`) | 없음 — 늘 네 모서리 |
| AI 가 컷을 고른 레시피 무비(`pipeline/trend_edit.py`) | 매치컷을 쓰는 레시피만, 컷을 이을 때 찾은 피사체(`_subject_box`) |
| 얼굴 스티커(`pipeline/face.py`) | 서버 안의 얼굴 검출(YuNet) — 얼굴만 |

그래서 "커피 옆에 꿀꺽", "케이크에 걸친 🍰" 같은 결정 문서의 그림이 나오지 않고, 스티커가 늘 같은 네 자리에 보인다.

## 2. 무엇을 정하나

1. 피사체 위치를 **어디서** 얻나 — 스냅 분석(외부 vision) · 렌더 때 로컬 검출 · 별도 호출
2. **모양** — 스냅 하나에 상자 하나인가, 분석한 프레임마다인가
3. **거르는 규칙** — 쓸모없는 상자(화면 전체 · 풍경)를 어떻게 버리나
4. **렌더에서 쓰는 법** — 원본 프레임 좌표를 결과물 화면 좌표로, 상자가 없을 때

## 3. 실측 — 루나가 주는 상자(2026-10-29)

`OPENAI_VISION_MODEL` 의 기본값 `gpt-5.6-luna` 에 실제 영상 프레임 12장(남원 · 몽골 · 일본 여행, 반려견)을 **한 장씩** 보내
"눈여겨볼 피사체 최대 3개의 이름 · 0~1 상자 · 확신도"를 구조화 출력으로 받았다. 분석과 같은 긴 변 512px · `detail: low` ·
`store: false`. 받은 상자를 프레임에 그려 눈으로 판정했다.

| 판정 | 장면 · 받은 상자 |
|---|---|
| 맞음 (9) | 기차 안 — 노트북 · 음료 컵 · 사람 / 비 오는 창밖 — 나무 · 교통 표지판 · 건물 / 남원역 — 역 건물 · 승용차 · SUV / 모닥불 — 불길 · 화덕 / 후지산 — 설산 · 호수 · 난간 / 팬케이크 — 팬케이크 · 시럽 주전자 · 시럽 줄기 / 맥주 건배 — 잔 무리 · 손 · 바텐더 / 텐트 안 강아지 — 작은 강아지를 딱 맞게 / 셀카 — 얼굴 · 선글라스(얼굴 상자는 넉넉함) |
| 쓸모없음 (2) | 노을 사막 — 하늘 · 모래언덕이 화면 절반씩 / 기념품 가게 — 화면 폭 전체의 가로 띠 셋 |
| 틀림 (1) | 아기 염소를 안은 장면 — 상자가 화면 전체, 이름은 "강아지" |

- **좌표의 일정한 어긋남은 없었다** — 맞은 상자는 실제 자리에 놓였다.
- **확신도는 구분력이 없다** — 모두 0.87~0.99, 틀린 "강아지"도 0.99.
- **비용 · 시간(한 장씩)**: 입력 363 토큰, 출력 116~330 토큰, 2.7~4.9초. 2026-10-26 확인한 단가(100만 토큰당 입력 $0.20 · 출력 $1.20 —
  [ai-edit-agent.md](ai-edit-agent.md))로 장당 약 $0.0003.
- 한계: 한 장씩 보냈다. 운영 분석은 스냅당 최대 4장을 **한 요청**에 시간순으로 보낸다(`pipeline/video_analysis/openai_client.py`
  `build_request`) — 그 형태에서 상자 품질과 기존 분석 필드가 그대로인지는 아직 재지 않았다(§6).

## 4. 선택지

| | 어디서 | 결과 | 비용 · 위험 |
|---|---|---|---|
| **A. 분석 응답에 상자를 더한다** (권장) | 지금의 스냅 분석 호출 하나에 프레임별 상자를 함께 받는다 | 한 번 구해 두고 모든 경로(사용자 컷 · AI 컷 · 미리보기 · 앱)가 같은 값을 쓴다. 렌더 시간이 늘지 않는다 | 추가 호출 없음, 출력 토큰 증가(스냅당 수백 토큰 ≈ $0.001 미만). 분석 프롬프트 · 스키마 · 계약 · 저장을 함께 바꾼다. 이미 분석된 스냅에는 없다 |
| B. 렌더 때 로컬 검출 | 워커가 편집본에서 물체 검출 모델로 찾는다 | 컷의 실제 프레임에서 찾아 시각이 정확하다 | 렌더 시간 증가. 일반 물체 검출 모델은 수십 MB 이고 널리 쓰는 YOLO 계열 일부는 AGPL — 라이선스 검토가 필요하다. 얼굴만이라면 YuNet(MIT)으로 이미 된다 |
| C. 상자만 따로 묻는 호출 | 분석과 별개의 vision 호출 | A 와 같은 상자 | 호출 수 두 배, 프레임을 한 번 더 보낸다(ANA-3 의 "보내는 것" 이 늘어난다) |
| D. 하지 않는다 | — | 지금처럼 네 모서리 | 없음. 꾸밈이 늘 같은 자리에 보인다 |

모서리 근처에서 자리를 조금씩 흔드는 임시 개선은 하지 않는다(2026-10-29) — A 가 들어오면 남는 효과가 거의 없고, 상자가 없을 때의
대체는 지금의 네 모서리가 이미 맡는다.

## 5. 권장안 — A 의 모양과 규칙

**모양 — 프레임별 상자.** 분석이 보낸 프레임마다(`video_analyses.frame_timestamps_ms` 와 같은 순서) 피사체를 최대 3개 받는다.
피사체는 움직이므로 스냅 하나에 상자 하나는 컷이 쓰는 구간과 어긋난다.

```json
"subjects": [
  { "frame": 0, "items": [ { "label": "노트북", "box": [0.344, 0.438, 0.754, 0.986] } ] },
  { "frame": 1, "items": [] }
]
```

- `box` 는 그 프레임 전체를 0~1 로 본 `[x0, y0, x1, y1]`(왼쪽 위 0,0). `label` 은 사람이 읽는 이름이고 **개념을 고르는 데 쓰지 않는다** —
  이모지 · 글은 지금처럼 `objects` · `actions` 등 목록 필드로 고른다.
- 확신도는 받지 않는다 — 실측에서 구분력이 없었다(§3).

**거르는 규칙 — 저장할 때 애플리케이션 검증으로.**
- 좌표를 0~1 로 자르고 `x0 < x1` · `y0 < y1` 이 아니면 버린다.
- **면적이 프레임의 60% 를 넘는 상자는 버린다** — 화면을 다 덮는 피사체(셀카 · 품에 안은 동물)와 풍경(하늘 · 모래언덕)은
  "피사체 옆" 이 없다. 실측의 쓸모없음 2 · 틀림 1 이 모두 여기에 걸린다. 값(60%)은 잠정이고 §6 실측으로 맞춘다.
- 너무 작은 상자(면적 0.5% 미만)도 버린다 — 옆에 붙이면 피사체와 상관없어 보인다.

**렌더에서 쓰는 법.**
- 컷의 원본 구간 가운데 시각에 가장 가까운 프레임의 상자를 쓴다. 여러 개면 **먼저 나온 것**(모델이 가장 눈에 띄는 것부터 준다).
- 원본 프레임 좌표를 결과물 화면 좌표로 바꾼다 — 맞춤 방식(`blur_background` · `pad_*` 는 가운데 맞춤 배율, `cover` 는 자른 만큼,
  레터박스는 띠 안). 화면 밖으로 잘린 상자는 남은 부분만, 다 잘리면 없음. 이 변환은 A-19 "원본 → 화면 좌표 하나로"(맞춤 방식별 `to_canvas`)와 같은 일이다.
- 상자가 없으면(이 결정 전에 분석된 스냅 · 동의하지 않은 스냅 · 걸러진 상자) 지금처럼 네 모서리. AI 컷 경로에서 매치컷이 찾은
  피사체가 있으면 그것이 먼저다 — 실제 결과물 프레임에서 찾은 값이라 더 정확하다.
- **얼굴은 여기서 다루지 않는다** — 얼굴 스티커는 지금처럼 YuNet. 루나의 얼굴 상자는 넉넉해 얼굴에 얹기에는 부족했다(§3).

**바꿀 곳(결정 뒤).** 스펙 MOV-27(피사체 옆에 붙는다) · ANA-2(분석 결과에 피사체 위치) → 분석 프롬프트 · 스키마
(`pipeline/video_analysis/prompt.py` · `schema.py`)와 `VIDEO_ANALYSIS_PROMPT_VERSION`(운영 시크릿 값 포함) → `video_analyses` 열 ·
계약 `packages/shared-types/src/contract/video-analyses.ts` · `apps/api/openapi.json` · [api-spec.md](../api-spec.md) → 워커 입력
(`db.fetch_accent_inputs`) · `accent_stage.build_cuts` · 좌표 변환. 분석은 다른 트랙과 함께 쓰는 영역이라 [team.md](../team.md) §1 의 담당을 확인한다.

**알려진 한계.**
- 분석은 동의한 스냅에만, 추천 · 초안을 요청할 때 돈다([snap-content-analysis.md](snap-content-analysis.md) §3) — 분석이 없는 스냅은 계속 모서리다.
- 프롬프트 버전을 올려도 이미 분석된 스냅은 다시 분석하기 전까지 상자가 없다. 스냅이 15일이면 만료되므로(SNAP-9) 따로 다시 분석하지 않는다.
- 상자는 분석한 4장 시각의 값이라, 그 사이에 크게 움직인 피사체와는 어긋날 수 있다.

## 6. 결정 전에 잴 것

운영 형태 그대로 — 지금의 분석 프롬프트 · 스키마에 `subjects` 를 더해 스냅당 최대 4장을 한 요청으로, 실제 스냅 10편 이상에서:

- 상자 품질 — 피사체가 뚜렷한 프레임에서 맞는 비율(목표 80% 이상), 60% 면적 규칙이 버리는 것 중 쓸 만했던 것의 수
- 기존 필드가 그대로인지 — 같은 스냅을 지금 프롬프트와 새 프롬프트로 분석해 `objects` · `actions` 등을 비교
- 출력 토큰 · 지연의 증가
